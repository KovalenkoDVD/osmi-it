# OSMI RAG Bot

Telegram-бот на **aiogram 3**, который отвечает на вопросы об OSMI IT и платформе OSMI AI.
Знания бот берёт из векторной базы на **PostgreSQL + pgvector**, в которую проиндексированы сайты
[osmi-it.ru](https://osmi-it.ru), [osmi-ai.ru](https://osmi-ai.ru) и документация
[docs.osmi-ai.ru](https://docs.osmi-ai.ru). Всё запускается в **Docker Compose** одной командой.

Ответы опираются только на найденные фрагменты. В каждом ответе есть ссылки `[1]`, `[2]` и список
источников с URL. Бот помнит контекст диалога, поэтому уточняющие вопросы вроде «а КПП?» тоже работают.

## Быстрый старт

```bash
cp .env.example .env        # впишите BOT_TOKEN и ANTHROPIC_API_KEY (или другой LLM, см. ниже)
docker compose up -d --build
docker compose logs -f bot
```

При первом старте бот сам обходит сайты и строит базу знаний. Это занимает примерно 5–10 минут на CPU:
скачивается модель эмбеддингов (~470 МБ, кэшируется в volume), затем индексируются ~1 500 чанков.
Пока база строится, бот отвечает «база ещё строится».

Полезные команды:

```bash
docker compose run --rm ingest          # инкрементально обновить базу (пересчитываются только изменённые страницы)
docker compose run --rm ingest --full   # переиндексировать всё
docker compose run --rm eval            # замерить качество поиска на контрольных вопросах
```

Команды бота: `/start`, `/help`, `/reset` (очистить историю), `/stats` (состояние базы),
`/reindex` (переобойти сайты; доступна только для `ADMIN_IDS`).

## Как это устроено

```
 сайты ──► crawler ──► extract ──► chunking ──► embeddings ──► PostgreSQL (pgvector + tsvector)
                                                                        │
 Telegram ◄── aiogram ◄── RAG: история + гибридный поиск (вектор ⊕ BM25, RRF) ──► LLM ──► ответ + источники
```

| Этап | Что делает | Файл |
|---|---|---|
| Обход | Асинхронный BFS по трём хостам. Стартует с главных страниц и всех URL из `sitemap.xml`, соблюдает `robots.txt`, скачивает PDF, на которые ссылаются сайты (реквизиты, презентация) | [app/crawler.py](app/crawler.py) |
| Извлечение | HTML превращается в блоки текста с уровнями заголовков. Скрипты, скрытые элементы и закомментированная вёрстка отбрасываются. Пары «Сотрудничество:» + «info@…» склеиваются в одну строку. PDF-таблицы разбираются в layout-режиме | [app/extract.py](app/extract.py) |
| Чанкинг | Повторяющиеся на всех страницах шапка, меню и подвал вырезаются и сохраняются **одним** отдельным документом. Контакты (`tel:`, `mailto:`, соцсети из подвала) собираются в документ «контакты». Текст режется по заголовкам (~1200 символов, перекрытие 200), у каждого чанка есть «хлебные крошки» `Страница > Раздел` | [app/chunking.py](app/chunking.py) |
| Эмбеддинги | `intfloat/multilingual-e5-small`, работает локально через fastembed/ONNX на CPU. API-ключ не нужен, данные не уходят наружу. Можно переключиться на любой OpenAI-совместимый `/embeddings` | [app/embeddings.py](app/embeddings.py) |
| Хранилище | `documents` + `chunks` (`vector(384)` с HNSW-индексом, `tsvector` для русского языка с GIN-индексом) + `messages` (история диалогов). У каждого документа хранится хэш: при повторной индексации пересчитываются только изменённые страницы | [app/db.py](app/db.py) |
| Поиск | Гибридный: косинусная близость в pgvector плюс лексический поиск с IDF-весами слов запроса (BM25-подобный, на Postgres FTS). Результаты сливаются через Reciprocal Rank Fusion, с одной страницы берётся не больше 3 чанков. Уточняющий вопрос ищется ещё и вместе с предыдущим | [app/retrieval.py](app/retrieval.py) |
| Генерация | Claude (`claude-opus-5-5`, effort `low` ради скорости) или любой OpenAI-совместимый API. Промпт требует отвечать только по источникам и ставить ссылки `[n]`. Под ответом выводятся только источники, на которые модель действительно сослалась | [app/rag.py](app/rag.py), [app/llm.py](app/llm.py) |
| Трейсинг | Langfuse (опционально): трейс на каждый вопрос, внутри него retrieval и generation с токенами, `user_id` и `session_id` | [app/tracing.py](app/tracing.py) |
| Бот | aiogram 3: команды, клавиатура с примерами вопросов, индикатор «печатает…», разбиение длинных ответов, фоновая первичная индексация | [app/bot.py](app/bot.py) |

### Что лежит в базе знаний

На момент проверки обход собрал 302 страницы. Из них получилось 308 документов и ~1 460 чанков:

- **osmi-it.ru**: 128 страниц: услуги, решения, 30+ кейсов, «О нас», контакты, реквизиты, блог (новости, лекции, статьи, комментарии);
- **osmi-ai.ru**: 6 страниц (платформа, готовые агенты, интеграции, кейсы, IT-раскрытие, политика) и 2 PDF: карточку предприятия с ИНН, ОГРН, банком и директором, а также слайд с интеграциями;
- **docs.osmi-ai.ru**: 166 страниц документации платформы (API, интеграции, Langfuse, настройка и т. д.);
- служебные документы: сквозная информация из шапки и подвала каждого сайта, плюс контакты и соцсети.

Что **не** попало в базу:

- презентация `osmi-it.ru/osmi-it.pdf` (29 МБ). Она состоит из картинок, текста в ней нет, а OCR не подключён;
- блоки, которые на сайте закомментированы в HTML и пользователю не видны. Например, ссылка на PDF «функциональные характеристики» на osmi-ai.ru.

## Качество поиска

[eval/questions.json](eval/questions.json) содержит 37 контрольных вопросов по фактам с обоих сайтов:
телефон, e-mail, адрес, ИНН/ОГРН/БИК, руководство, аккредитация, цены, награды, кейсы, возможности OSMI AI,
сроки внедрения, поддерживаемые LLM, документация API и т. д. Проверяется, попадает ли нужный факт
в контекст, который получает LLM (top-8):

| Поиск | hit@8 | MRR |
|---|---|---|
| только вектор (e5-small) | 86% | 0.66 |
| только лексический (IDF-взвешенный FTS) | 81% | 0.66 |
| **гибрид (RRF)** | **95%** | **0.81** |

Как подбирались параметры:

- Первая версия лексического поиска на `ts_rank_cd` давала 49% и **ухудшала** гибрид до 77%. Частые слова («платформа», «OSMI») перевешивали короткие точные чанки. После перехода на IDF-взвешивание лексический поиск вырос до 80%, а гибрид до 89%.
- Константа RRF уменьшена с 60 до 20 (+1 вопрос). Увеличение top-k до 10 ничего не добавило.
- Сквозные телефон и e-mail из шапки убраны из каждого чанка: значения на странице «Контакты» остаются за счёт склейки «метка: значение». MRR гибрида вырос с 0.76 до 0.79.
- Исправлена потеря подзаголовков при склейке мелких секций. Раньше из списка решений пропадало название продукта, а у списка модулей — заголовок «OSMI AI для девелопмента». Теперь путь заголовков печатается деревом, новый раздел начинает новый чанк, а повторяющиеся кнопки («Перейти к решению») вырезаются. Результат: hit@8 вырос с 91% до 95%, MRR с 0.79 до 0.81.
- `multilingual-e5-base` на этом наборе дал гибрид 86% против 91% и индексировался вдвое дольше, поэтому по умолчанию стоит e5-small. `e5-large` на CPU слишком медленный (~0.8 чанка/с).

Оставшиеся промахи: «почта для сотрудничества» (маленькая модель не связывает «почта» и «e-mail») и перечень
интеграций OSMI AI.

## Локальная LLM в контейнере (без API-ключей)

```bash
# в .env: LLM_PROVIDER=openai, LLM_MODEL=qwen2.5:3b, OPENAI_BASE_URL=http://ollama:11434/v1, TOP_K=4
docker compose --profile local-llm up -d    # Ollama + одноразовая загрузка модели (~1.9 ГБ)
```

Модель ничего не знает о компании. Без контекста на «Какой ИНН у ООО «ОСМИ-ИТ»?» и «Кто гендиректор
OSMI IT?» `qwen2.5:3b` отвечает, что такой информации у неё нет. Через RAG она отвечает по найденным
фрагментам:

| Вопрос | Ответ qwen2.5:3b (TOP_K=4) | Время |
|---|---|---|
| Какой телефон у OSMI IT? | +7 (495) 128-19-89, +7 (958) 111-87-51 [1][2][3] | 4.5 с |
| Где находится офис? | Москва, ул. Автозаводская 23Ак2 [2] | 2.0 с |
| Куда писать по трудоустройству? | hr@osmi-it.ru | 11 с |
| Какой ИНН у ООО «ОСМИ-ИТ»? | 6317139806 [1][2][3][4] | 29 с |

Замеры сделаны в Docker Desktop на Mac: 4 CPU, без GPU. Скорость упирается в чтение промпта (~40 токенов/с):

- при 8 фрагментах промпт занимает около 3 000 токенов, и ответ идёт около минуты;
- поэтому для CPU стоит `TOP_K=4`. Поиск при этом находит факт в 86% случаев вместо 95%.

Где модель слабее Claude:

- иногда не ставит ссылки на источники;
- плохо переписывает длинные списки. Например, из 6 модулей «OSMI AI для девелопмента» может назвать 4, хотя полный список есть в контексте. Для таких вопросов нужна модель от 7B или Claude;
- если поиск не нашёл нужный фрагмент, может уйти в сторону. На «почту для сотрудничества» она пересказала
  документацию про SMTP, хотя адрес не выдумала.

Как ускорить:

- на Linux-сервере с NVIDIA GPU добавить сервису `ollama` доступ к видеокарте (`deploy.resources.reservations.devices`);
- на Mac запустить Ollama нативно (Metal) и указать `OPENAI_BASE_URL=http://host.docker.internal:11434/v1`.

## Настройка (.env)

| Переменная | По умолчанию | Описание |
|---|---|---|
| `BOT_TOKEN` | — | токен от @BotFather |
| `ADMIN_IDS` | — | Telegram ID через запятую, кому доступен `/reindex` |
| `LLM_PROVIDER` | `anthropic` | `anthropic` \| `gemini` \| `openai` (любой OpenAI-совместимый API) \| `none` (без LLM: бот отвечает цитатами) |
| `LLM_MODEL` | `claude-opus-5-5` | модель (для `openai` можно указать `gpt-4o-mini`, `deepseek-chat`, модель Ollama и т. п.) |
| `LLM_EFFORT` | `low` | effort Claude: `low` \| `medium` \| `high` |
| `ANTHROPIC_API_KEY` | — | ключ Anthropic |
| `GEMINI_API_KEY` | — | ключ Google Gemini из [AI Studio](https://aistudio.google.com/api-keys) (для `LLM_PROVIDER=gemini`) |
| `OPENAI_API_KEY`, `OPENAI_BASE_URL` | — | для OpenAI / OpenRouter / DeepSeek / Ollama (`http://host.docker.internal:11434/v1`) |
| `EMBEDDING_MODEL`, `EMBEDDING_DIM` | `intfloat/multilingual-e5-small`, `384` | при смене модели векторы удаляются автоматически, после этого нужен `ingest` |
| `START_URLS`, `ALLOWED_HOSTS` | три сайта OSMI | что обходить |
| `TOP_K`, `RRF_K`, `CHUNK_SIZE` | `8`, `20`, `1200` | параметры поиска и нарезки |
| `HISTORY_TURNS` | `4` | сколько предыдущих пар «вопрос–ответ» учитывать |
| `LANGFUSE_PUBLIC_KEY`, `LANGFUSE_SECRET_KEY`, `LANGFUSE_HOST` | — | включают трейсинг |

Если запросы к Claude отклоняются фильтрами безопасности, включается серверный fallback на другую модель
(`LLM_REFUSAL_FALLBACK=true`). Если LLM недоступна, пользователь видит ошибку и самые релевантные цитаты:
бот всё равно отвечает.

## Разработка

```bash
uv sync
docker compose up -d db
uv run python -m app.ingest     # локальная индексация (DATABASE_URL из .env указывает на localhost)
uv run python -m eval.run_eval  # метрики поиска; --answers дополнительно сгенерирует ответы LLM
uv run python -m app.bot
uv run pytest                   # 14 тестов: парсинг, чанкинг, robots, RRF, форматирование, LLM-адаптеры на HTTP-стабе
uv run ruff check . && uv run ruff format --check .
```

```
app/
  bot.py          Telegram-бот (aiogram 3)
  rag.py          промпт, сборка контекста, ссылки на источники, HTML для Telegram
  retrieval.py    гибридный поиск + RRF
  llm.py          Anthropic / OpenAI-совместимые адаптеры
  embeddings.py   fastembed (локально) / OpenAI-совместимые эмбеддинги
  db.py           схема, pgvector, полнотекстовый поиск, история
  ingest.py       crawl → chunk → embed → upsert (инкрементально)
  crawler.py      обход сайтов, sitemap, robots.txt, PDF
  extract.py      HTML/PDF → структурированные блоки
  chunking.py     очистка шаблонного текста, документы-контакты, нарезка
  tracing.py      Langfuse
eval/             контрольные вопросы и замер hit@k / MRR
tests/
```

## Что можно улучшить

- **Реранкер** (multilingual cross-encoder поверх 30 кандидатов). Должен закрыть синонимические промахи, но добавит 1–3 с к ответу на CPU.
- **OCR** для презентаций из картинок (`osmi-it.pdf`).
- **Периодическая переиндексация** по расписанию: инкрементальная индексация уже есть, остаётся cron или APScheduler.
- **Оценка ответов, а не только поиска**: LLM-as-judge на ответах из `eval --answers`, с выгрузкой оценок в Langfuse.
